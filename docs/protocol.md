## 4. Known lobby protocol format (JP, per Bioserver1) [FACT for JP; unverified on US]
- Transport: TCP. 12-byte big-endian header: `who(1) qsw(1) cmd(2) len(2) pid(2) err(1) ff ff ff`. `len` = payload length.
  - `who`: 0x18 SERVER, 0x81 CLIENT, 0x28 GAMESERVER, 0x82 GAMECLIENT (`Commands.java`).
  - `qsw`: 0x01 QUERY, 0x02 TELL, 0x10 BROADCAST. Reply TELLs reuse the QUERY's `pid`.
- Strings: `len16 (= n+2), sum16, n bytes`, encrypted with an XOR that depends on the index and on `pid & 0xff` (`Packet.calc_shift`). The server does not verify `sum16`; its algorithm is unknown.
- In game (gameserver), frames have no header: the first byte is the total length. Only `GSLOGIN` uses the 12-byte header.
- **[FACT, validated against our Bioserver-derived server]**: the header, the cipher (indices 0..0xCF, including the signed-byte branch), the session obfuscation in LOGIN/GSLOGIN, the full login up to 0x6104, areas, rooms, slots and the relay all pass with `tools/testclient.py`, 23/23 on File #1 and File #2. Details in [server.md](server.md). This confirms we understood the Bioserver implementation; it confirms **nothing** about the US client.
- Flow:
  1. Web login (KDDI -> PHP) that creates the session.
  2. TCP to the lobby: `LOGIN 0x6101` -> `CHECKVERSION 0x6103` (optional patch 0x6121-0x6125) -> ID/HN 0x6131/0x6132 -> MOTD 0x614C -> `CHARSELECT 0x6190`.
  3. Areas 0x620x -> rooms 0x630x -> slots 0x640x/0x650x -> rules 0x660x -> chat 0x670x.
  4. `GETREADY 0x6910` ... `GSINFO 0x6916` (gameserver ip:port).
  5. TCP to the gameserver: `GSLOGIN 0x1031`, with the session obfuscated as `sess+seed` in decimal ASCII. Then opaque relay.
- Coverage: `Commands.java` defines 96 commands, 14 of them `UNKNxxxx`. **About 85% of JP lobby messages have a name/semantics.** In-game traffic is 0% interpreted, but the server does not need to understand it (relay).
- **For SLUS:** the US client uses different protocols (sections 6 onward).

## 6. US client: captures (2026-10-16)
**[FACT, captured and read in SLUS_207.65]** The first US client service is `app01.reo.capcom.sf.yav4.com:**10127**` (host and port at `0x1F68D8`, port `0x278F`). The client is ELF code (`0x1F4600` recv, `0x1F6B10` state machine), not netwk.bin. **The server speaks first.**
- **8-byte** header (vs 12 in JP): `len16(BE, payload only) qsw cmd16 pid8 err8 0xFF`. Same `qsw` values (01 QUERY, 02 TELL which copies the pid, 10 BROADCAST), but there is no `who` byte and the pid is 1 byte. The client rejects the JP header: it reads `0x1801` as a length and waits.
- Strings: `len16(n+2) sum16 data`, as in JP, but the cipher differs: `b ^ "MINAMIOH"[i&7] ^ (seed+pid+i)`. The key is the base64 `TUlOQU1JT0g=` (in the ELF) and `seed` is the u16 the server sends in QUERY 0x1002. The checksum is `(sum(plain)+pid*257) & 0x7FFF` and **the client verifies it**. Checked with a real TELL 0x1002: string "0404141723", sum 0x03FC.
- Message table at `0x237330..0x2373B0` (28 entries: qsw, cmd, handler). The server sends QUERY 1001/1002, TELL/BCAST 1004, BCAST 1005, BCAST 6001, TELL 6002/6101/6102/6201/6202/6301/6401/6402 and BCAST 6110/6210. The client sends the TELLs of 1001/1002 and the QUERYs 1004/6002/6101/6102/6201/6202/6301/6401/6402.
- Captured sequence against the prototype server (`usapp.py`): S QUERY 1001 -> C TELL 1001 -> S QUERY 1002 [seed] -> C TELL 1002 (empty string, 01 01, "0404141723", 00000000) -> S BCAST 6001 [00] ("nothing to download") -> C QUERY 6101 (24 bytes) -> S TELL 6101 [00] -> **the client hangs up** (~45 s later, DHCP RELEASE).
- It belongs to the **same family** as Bioserver's protocol (qsw, 0x6xxx cmds, strings with sum and XOR), with a different variant.

### 6.1 app01:10127 is a downloads/news service, not the lobby (2026-10-16)
**[FACT, read in SLUS_207.65 and verified in a run]** The message table at `0x237330` is a struct-of-arrays of 28 entries: `cmd_hi[28]` at 0x237330, `cmd_lo[28]` at 0x237350, `dir[28]` at 0x237370 (08 = client sends, 01 = client receives), `qsw[28]` at 0x237390 and `handler[28]` at 0x2373B0. The dispatcher at `0x1F6CBC` compares qsw, cmd_hi and cmd_lo with header bytes 2, 3 and 4. If the handler returns < 0 the machine goes to state 7 (error) with that code at `+0x8C`; returning 1 advances the major state; 0 stays. Sub-states (`+1`, jump table `0x259BA0`, 21 entries) send the QUERYs: 2->6002, 4->6401, 6->6402, 8->6201, 10->6202, 12->6101, 14->6102, 16->6301, 18->1004.
Payload readers (cursor at `+0x34`): `0x1F47E0` u8, `0x1F4830` u16 BE, `0x1F4890` u32 BE and `0x1F4910` string (`len16 sum16 data`, with a maximum).
Many handlers reject the TELL if `err` (header byte 6) is 0xFF.

| cmd | direction | format (fact) | semantics |
|---|---|---|---|
| 1001 | S QUERY -> C TELL | empty | greeting (fact) |
| 1002 | S QUERY `u16 seed` -> C TELL | TELL: empty string, `01 01`, string "0404141723", u32 0 | XOR seed (fact); rest of the TELL [HYPOTHESIS: client version/id] |
| 6001 | S BCAST | `u8` 0 = nothing to download | 0 -> sub-state 0xC (6101) (fact). Nonzero: download via 6002 [HYPOTHESIS: patch/update] |
| 6101 | C QUERY -> S TELL | Q: `u32 0`, name string ("01/TOP_INFOR.HTM"). T (`0x1F60B0`): `u8 exists`, `u32 ?`, name string (must match, else -0x3D), `u32 size` | **0 -> error -0x3E and the client hangs up** (this was the blocker). Size 0 -> sub-state 6; otherwise 0xE (6102). Block = `0x2FE - (strlen(name)+12)`. Buffer `*(0x3557C0)`, cap 0x1000 (0x8000 if `*(0x35EAF0)==2`) |
| 6102 | C QUERY -> S TELL | Q (captured): name string, `u32 offset`, `u16 block` (0x2E2 for TOP_INFOR.HTM). T (`0x1F6420`): name string, `u32 offset` (must equal the client's, else -0x3C), string with the block (last = size - offset) | HTML news page. When done: mode 2 -> 1004; otherwise -> 6401 |
| 6401 | C QUERY (empty) -> S TELL | T (`0x1F54F0`): `u16 n`, n x `u32` (sizes, at 0x35EBB4) | n = 0 -> 6201; otherwise -> 6402 (n messages of up to 1 KB at 0x355AD0). An empty TELL works (reads 0). [HYPOTHESIS: operator messages] |
| 6402 | C QUERY -> S TELL | Q: `u8 index`, `u32 offset`, `u16 0x2F2` | block download of each 6401 message (untested) |
| 6201 | C QUERY -> S TELL | Q: string (empty in the capture, buffer 0x259B38). T (`0x1F59C0`): `u8 has`; if nonzero: string (<=0x1F), `u16 n` (<=3), n x `u32 size` | 0 -> sub-state 0x12 (1004) (fact). Up to 3 files of <=8 KB at 0x357AD0 |
| 6202 | C QUERY -> S TELL | Q: `u8 index`, `u32 offset`, `u16 0x2F2`. T (`0x1F5C20`): `u16 index`, `u32 offset`, block string (<=0x2F2) | download of the 6201 files (untested) |
| 6301 | C QUERY -> S TELL | Q: 3 bytes, string, 2 bytes, 2 x u32, 3 x (string, 2 bytes), 8 x u32. T (`0x1F67D0`): ignores the payload | [HYPOTHESIS: stats/ranking report]; always -> 1004 |
| 6110 | S BCAST | `u16` (0 -> 100) at 0x33C7F8 and string (<=0xFF) replacing the `snap01...` host at 0x33CC60 | the server can redirect the next host (by code, untested) |
| 6210 | S BCAST | handler `0x1F5E30` | unread |
| 1004 | C QUERY (empty) -> S TELL (empty) | TELL -> handler returns 1 (end OK). BCAST 1004 -> -1 (disconnect) | end of the app01 session |
| 1005 | S BCAST | handler `0x1F5050` | unread |

**Verified sequence:** 1001 -> 1002 -> BCAST 6001 [00] -> 6101 (TOP_INFOR.HTM, 87 bytes) -> 6102 (one block) -> 6401 (empty TELL) -> 6201 (empty TELL = `00`) -> 1004 -> **the client closes cleanly**, resolves `snap01.reo.capcom.sf.yav4.com` and shows the DNAS legal text (5 pages) and "Will you agree to DNAS EULA?". ### 6.2 regweb and the "MMBB" browser (2026-10-16)
**[FACT, captured]** With the runtime fix below, the netwk.bin browser (BIN_3, `User-agent: Y/K/Browser 1.50 for OBUSA`) does `GET /reweb/index.jsp HTTP/1.0` to regweb:80. If the response is the JP page `<!--CRS-game-start-->` with CSV `"OK","<session>","<enterareas url>","<exit url>"`, the browser does `POST /reweb/enterareas.html` with `connection-id=<session, each digit %XX>&user-id=` (empty). It replies `<!--CRS-lbs-info-get-->` (same CSV as Bioserver) and **the game returns to the NETWORK menu without opening TCP to a lobby**.
- **[FACT]** The NETWORK menu starts with the cursor on EDIT ACCOUNT and "up" does not move it: **GO ONLINE cannot be chosen without an account**. The two requests above came from EDIT ACCOUNT.
- **[FACT, BIN_3 loaded at 0x570000]** Page-type table at `0x60DC60` (pairs of name pointer and id): CLOSE-PAGE 0x0C, CRS-GAME-START 0x0D/0x0E, CRS-LBS-INFO-GET 0x10, CRS-GAME-END 0x11, CRS-TOP 0x12, CRS-MENU 0x13, CRS-COURSE-* 0x14-0x1E, CRS-MMBBCHARGE-* 0x1F/0x20, CRS-ERROR 0x21, **AM-USA-COMP-SIGNUP 0x25**, INPUT-SFIELD 0x28, **COMP-LOGIN 0x29**, KEICAN/CANCAN-MMBB 0x2A/0x2B and CHG-IMG-BUTTON-1..4 0x2C-0x2F. - **[FACT]** `mmbb://` links are resolved at `0x597300...` (browser mode at `*(*(0x67C2B8)+0x2E)`; 0x0A = EDIT ACCOUNT, 8 = another mode, GO ONLINE?): `REGIST_CHECK?` checks that the account fields `[0x00]`, `[0x41]`, `[0x4C]`, `[0xCD]`, `[0x14E]`, `[0x14F]` are non-empty; `NEW_REGU_OK` and `NEW_REGU_NG` (in mode 0x0A) change state; `GAME_MENU_<n>` returns to menu n; `BUTTON_OK` copies the account (0x1D0 bytes) to `0x8A6BF0`. Other links: `EXIT;`, `BB_DOD_KIYAKU` (opens `file://DATA/KIYAKUBB.HTM`), `BUTTON_NG`, `BACK_TO_MENU`.
- **[FACT]** The account is a 0x1D0-byte structure pointed to by `*(0x67C2D0)`. Page `<input>` elements with a 2-digit numeric name are filled from the structure (`0x58F1C0`, table `0x622440`) and, when edited with the on-screen keyboard, written to it (`0x5A1EE0`, table `0x622C00`): 00 -> +0xCD, 01 -> +0x00, 02 -> +0x14E (number), 03 -> +0x41 (8 bytes)... [HYPOTHESIS: 01 is the ID, 03 the password, 00 the handle or mail].
- **Injection experiment:** with `PS2_POKE`, "test1" was loaded into the account fields; regweb served a page with `<a href="mmbb://NEW_REGU_OK">`; the browser showed it with the link focused and pressing X opened a two-button box (no visible text). [HYPOTHESIS: "save the account to the memory card?"]
- **[FACT]** That box **does not respond** to X, O, left or right (2000+ frames) and there is no memory-card activity. With `NEW_REGU_OK` the browser moves to state 9 (byte `*(0x67C2B0)+0x68E85`; switch at `0x5A2BF0`, table `0x622C30`), which draws the box with texts `0x5A3AA0(7,5)` and `(7,6)`, which come out empty. [HYPOTHESIS: the browser message table was not loaded (AFS `afs://02/...` in NETBIO02.DAT?), or the state waits for something we injected wrongly]. This path became moot once 6.4 found the real account store.

That is why TCP to regweb opened but the GET was never sent. ExitThread is now applied, like the real kernel. Also, `PS2_PACE=<frame>` limits speed to 60 Hz (the network lives in real time) and `PS2_POKE` writes to EE RAM at a given frame.

### 6.4 Account on the card, GO ONLINE and US login over UDP 9090 (2026-10-16)
**[FACT, read in BIN_3 and verified in runs]**
- **Where the account lives.** The network system save `mc0:/BASLUS-20765NET/BASLUS-20765NET` (0x1D7C bytes, descriptor at `0x2350B0`, **no checksum**) is loaded as-is at `0x38CD90`. Fields used by BIN_3: `+0x000` list of 50 x 0x38 (friends/blocked, copied to `0x6A2780`), **`+0xAF0` account ID (string, 20 bytes)**, `+0xB04` and `+0x1840` 0x208-byte copies of the netcnf state, `+0xE0E` flag ("previous connection"), `+0xE20` netcnf block (contains "SCE" and "Ethernet (Network Adaptor)").
- **GO ONLINE.** The NETWORK menu (menu 13 of table `0x6187E0/0x6188E0`; code at `0x607EDC`) does `if (NET[0xAF0]==0) cursor=EDIT ACCOUNT and "up" blocked; else strcpy(0x8A64F0, NET+0xAF0)`. **A non-empty ID at +0xAF0 is enough** to enable it. The 0x1D0-byte structure at `0x8A6BF0` is only the sign-up form (browser) and is not saved to the card. Proof: patched card -> GO ONLINE enabled with the cursor on it.
- **Runtime** (`ps2-web-recomp/runtime/src/iop/netcnf_card.cpp`): with networking enabled, if the NET save exists and `+0xAF0` is empty, it writes `PS2_NET_ACCOUNT` (default `player`; `[A-Za-z0-9_-]`, <=19). It never overwrites an existing ID. ### 6.5 kkClient 2.1: transport, encryption and login (2026-10-16)
**[FACT, read in SLUS_207.65 and verified in a run]** Prototype: `server/tools/kkudp.py`.
- **Datagram** = one or more messages + a u32 BE trailer `0xBA4766xx` (the receiver at `0x1DD6xx` requires `& 0xFFFFFF00 == 0xBA476600`, that the source be exactly the server IP:port at `ctx+0x4C/0x4A`, and that the datagram be >= 0x14 bytes). No checksum.
- **Message header (16 bytes, all BE)**: `u16 flags|len` (len = 16 + payload, `& 0x3FF`), `u16 type` (bits 0-6 = type; high byte = request id, see 6.6), `u32 tag` (the client puts the low half of its IP + port), `u32 seq`, `u32 ack`. Flags: `0x8000` reliable (ordered seq, queue `ctx+0x5C/0x60`), `0x4000` carries an ack at +12 (`0x1E78F8`), `0x0800` packet with sub-messages, `0x1000`/`0x2000` set by the client (0x2000 = trailer appended). An unreliable message is accepted if `seq >= ctx+0x10` (last seen). `0x1F3BCC` walks several messages per datagram.
- **Dispatch by type**: switch at `0x1DFDA8`, table `0x257D00` (type-3, 0x76 entries). Types with a handler: 03-0C, 0E, 0F, 10, 12, 13, 14, 25, 27, 28, 29, 2D, 2E, 31, 32, 35, 40, 43, 47, 48, 49, 6E, 78. The client sends (API functions calling `0x1E763C(ctx, msg, flags, len, type, 0)`): 01, 02-14, 25, 2C, 32, 34, 3E, 3F, 41, 43, 46-49.
- **Encryption: standard Blowfish** (P tables at `0x258170`, S at `0x2581B8`; init `0x1EB064`, encrypt `0x1EAE08`, decrypt `0x1EAF34`), **ECB with big-endian words** (`0x1EB368` decrypts, `0x1EB4F8` encrypts). **Key = the password as is** (`ctx+0x484`, strlen). Not standard Kerberos/DES; a custom scheme shaped like Kerberos (AS -> ticket -> service).
- **Login**: C `0x2C` (unencrypted): `+0x00` name (0x28), `+0x28` `name@cei-auth` (0x3C), `+0x64` 0xCAE0, `+0x6C` IP, `+0x70` port, `+0x74` 100, TLV. S `0x2D` (handler `0x1DF4A8`, requires `ctx+0x80 == 1`): payload from +0x10 encrypted with the password. Plaintext: `+0x00` name (compared with the login name: mismatch -> result 0x27 = wrong password), `+0x28` u32 session-server IP -> `ctx+0x500`, `+0x2C` u32 port -> `ctx+0x504`, `+0x32` u16 new auth port (0 = same), `+0x34` u32 ticket length, `+0x38` u32 -> `ctx+0x508`, `+0x3C` ticket (opaque). `0x2E` = login error.
- **Session connection**: the client sends `0x01` (`0x1DCD10`) to the IP:port from `+0x28/+0x2C` with the `ctx+0x84` structure (0x128 bytes + ticket) and TLV `MR`/`LC`. S `0x29` = accepted: `u32 port (0 = same), u32 (forced to 1), u32 -> ctx+0x44`; calls the login callback (`ctx+0x5B8`) with result 0. `0x27` = error and `0x28` = generic reply: `u32 request type, u32 status, ...` -> switch `0x1E0E78` (0x49 entries) calling that request's callback. `0x31` = disconnect with error.
- **Result**: password "1111". 0x2C -> 0x2D -> 0x01 -> 0x29 and **the game reaches SERVER SELECT** ("DOWN TOWN / SCENARIO MODE SERVER").
- **After login**: X on SERVER SELECT -> C `0x0D` reliable (`flags 0xA000`, tag = the u32 we gave in `0x29`) with `u32 0xF7E00001` (join group/service?). Without an ack it is retransmitted every 2 s. Ack = a message with `0x4000` and `ack = seq` exactly (exact lookup in the queue, `0x1E78F8`). Accepted reply: `0x28 [u32 0x0D, u32 0]` -> BIN_3 callback `0x5841E0` -> NEW GAME / LOAD GAME / DATABASE menu -> CHARACTER SELECT. Then the client sends `0x0C` (240 bytes, reliable; profile), `0x14` unreliable every ~1 s (64 bytes `00 55 55...`, presence?) and **`0x48` = directory query**.
- **`0x48` (query)**: Q: `u32 max, u8 n, 3 pad, n x (char[4] field "NAME", u8 operator, char[16] value)`. Operators seen: `'A'` (=), `'D'` (>=), `'F'` (<=). R: message **`0x48`** (handler `0x1E053C` -> `0x1DEA40` -> callback slot 0x31): `u32, u32, u32 n` + n x 0x24 bytes (`char[16] name, u32 +0x10, +0x14, +0x18, +0x1C, +0x20`). ### 6.10 Errors and disconnections (2026-10-18/19)
**Problem:** if the owner closed the browser, the room stayed in the list until the inactivity expiry and anyone entering got stuck for a while.
- **Disconnect detection [FACT]:** a client on the area or room list sends nothing, so the server sends it a **reliable ping** (`0x28 {0x14, 0}` with flag `0x8000|0x1000`, the harmless presence reply, now in the client's reliable sequence) after 8 s without traffic; the client acknowledges with a bare ack (`0x4000`, ~40 ms natively) and that counts as traffic. **With no traffic at all for `us.kk.dead_secs` (30 s by default) the session is dropped.** No false drops were seen in native runs at ~5 fps with minutes-long waits on lists.
- **Owner leaves a waiting room [FACT, verified]:** the room closes (type-5 push to the area) and each member receives a reliable `0x10` "as if from the owner" `{u32 1, u32 member id, u8 0x0D, 0, 0, 0}` = class **0x0D**, which the owner's game sends when it disbands (seen in a user pcap). BIN_3 `0x58395C` (class table `0x621A60`) shows **"The room has been disbanded by the host."** (if `0x679351` is nonzero, set by the entry callback `0x587A10`) and goes to state 0xB (room list). Verified: A killed mid-room, 30 s later the server logs the disconnect and the room disband, B shows the message and returns to an empty ROOM LIST.
- **Someone leaves mid-game [FACT]:** with the usual `0x07 {id}` push (member left), **the remaining player's game crashes**: B died with `missing code at 0x00000000`. During the scenario BIN_3 (lobby) is not loaded and the slot of push `0x07` is empty or points nowhere [HYPOTHESIS: a real PS2 would hang too]. **Fix:** while the room is in game the server does not send `0x07` to members; the departed player leaves the room and the room closes when empty. **Verified:** A killed mid-game; the server drops it after 30 s and **B keeps playing**: the scenario removes the character from the scene by itself and B runs on without a crash.
- **Entering a room that no longer exists, is full or started [FACT, protocol test]:** `0x27 {0x06, 1, 0}` -> "You couldn't enter the room" and back to the list (same callback as the password, 6.9). Nonexistent room = OID >= 0x1000 not in the table (previously the server treated it as entered).
- **List after leaving a room [FACT, old bug]:** when returning to the list the client sends `0x07` and `0x0B {area OID}`; the server set `cur = 0` and the player stopped receiving list pushes. Now `0x07` from a room leaves the player in that room's area, and `0x0B {area}` places them in that area if not in a room.
- **Same name connected twice [FACT]:** a `0x01` with a name that already has a session (browser reload, reconnect) closes the old session with the same treatment as a disconnect (leaves the room; if owner of a waiting room, disbands it). `0x02` (goodbye) also.
- **Robustness [FACT]:** the UDP loop catches `Throwable` per datagram and the `tick` (resends, ping, expiries) has its own try; invalid lengths (< 16 or past the datagram) drop only that datagram; an `IOException` in `receive` does not stop the loop. app01: a malformed request closes only that connection, with a cap on simultaneous connections.
- **Protocol test (no game):** nonexistent room -> `0x27 {6,1}`; 20 malformed packets (empty, short, length 0x3FF, length < 16, short payloads for 0x06/0x48/0x0B/0x25/0x04/0x09/0x10/0x2C, type 0x7F, unknown tag) + 300 random datagrams with a valid trailer -> the server keeps answering; same name reconnecting replaces the old session; a client that acknowledges pings stays alive and one that does not drops after 30 s.
- **Security hardening [FACT]:** the kk service was hardened against spoofing, amplification and flooding. Protocol-visible parts: the 0x2D reply carries a random per-login ticket at `+0x3C`, which the client returns in `0x01` (payload `+0x24` u32 length 16, `+0x28` ticket) and which must be valid for that name; session tags are random; requests that need a session get no answer without one. The server also applies rate limits and caps; the production tuning is intentionally not published. A local fuzz test confirmed no takeover without the credential, no amplification from unauthenticated packets, and the service staying responsive under garbage floods.
- **Not covered / hypotheses:** a global per-real-IP UDP limit (behind the gateway everything arrives from 127.0.0.1 with one port per flow; the gateway limits frames and bytes per second); a gateway crash looks like a disconnect of everyone after 30 s; a game room that loses everyone closes when empty.

### 6.11 Host lost mid-game, orphan rooms, unique titles (2026-10-22)
**Report:** "if the room host disconnects, everyone else gets stuck: they cannot pick up items and enemies do not move".
- **Cause [FACT by code; no game run reproduces it]:** in game the server notifies nobody (on purpose, 6.10: the `0x07` push in a scenario kills the client). The scenario only detects a dropped partner by silence, and **the runtime raised that timeout to 300 s** (File #1: float 20.0 at `0x235F50`; File #2: 31.0 at `0x241280`) to tolerate slow loads in the browser. So the others wait up to 5 min for a host that is gone, and the host is the one that moves enemies and confirms items. With the native 20 s timeout, B kept playing alone after A dropped.
- **Second softlock [FACT by code]:** when the scenario ends, members return to the waiting room (0x0D, 0x0C, 0x0A), whose owner is gone, and nobody can press START.
- **Server (`KkService`) [FACT, protocol test 13/13]:**
  - If a member leaves a room in game for good (`drop`: no traffic, `0x02`, replacement, BYE plus grace; or `0x07` in game), `peerGone()` sends to each other member's address the datagram **`"REOGW-GONE"` + u32 BE tag of the one who left**, with no kk header or trailer. Config `us.kk.peer_gone_notice` (true by default). Only meaningful behind the gateway: a direct UDP client would receive and discard it as junk [HYPOTHESIS: kkClient discards datagrams without the trailer].
  - If the departed one is the owner, the room becomes an **orphan** (`hostGone`): it leaves `0x0B`, `0x49` LOID, resyncs and pushes (counts as type 5), and a `0x06` to it gives `0x27`.
  - When a member asks `0x0A` of an orphan room (return from the scenario), it receives the member list and then the **host disband**: reliable `0x10 {1, its tag, 0x0D,0,0,0}` with the old owner's tag in the header (same as `disband()`, 6.10). The server moves it to the area and closes the room when empty.
- **`REOGW-RTT`:** gateway -> kk on each UDP flow every 15 s: `"REOGW-RTT"` + u32 BE ms (browser <-> gateway RTT). The kk stores it per address and per game member and adds it to the game stats (estimated one-way delay); see network.md §14.
- **Gateway (`net/gateway`) [FACT, `TestUpstreamControl`]:** an upstream datagram starting with `REOGW-` never goes to the guest. `REOGW-GONE`+tag becomes the WebSocket **text** message `{"type":"kk-peer-gone","tag":"xxxxxxxx"}`, sent through the same writer with a 16-deep queue that drops when full. Runtimes initially ignored text messages (the web runtime returns on `isText`; the native one only queues opcodes 0x0/0x2), so it was harmless until the runtime used it (see 6.15).
- **Runtime request (implemented later, see 6.15/6.16):** on receiving `kk-peer-gone`, temporarily return the partner timeout to the native value (File #1 `0x235F50` = 20.0f, File #2 `0x241280` = 31.0f) for ~40 s, then back to 300 s. Safe even on a false positive, because an active partner is never silent for >= 20 s. Alternative: age the "last heard" stamp of that partner (File #1: table `0x335050 + 0x3C*i`, field `+0x54`).
- **Hypotheses pending a game run:** (a) a client returning from the scenario shows "The room has been disbanded by the host." with the `0x10` 0x0D (BIN_3's handler needs `0x679351` nonzero, and BIN_3 is reloaded after the scenario); (b) the scenario continues fine without the host once the runtime shortens the timeout (it did in the native test); (c) no other "host" of the scenario is chosen by the game.
- **Duplicate titles [FACT, test]:** a `0x04` with a title already in the area (case-insensitive) gets the suffix " 2".." 99" (trimmed to 15 characters). The handler is single-threaded, so there are no creation races server-side. "Rooms on top of each other" in File #2 may be the QUICK START race of section 7 (client behavior) [HYPOTHESIS].
- **List resync [FACT]:** the periodic list resync went from 15 s to 5 s. In File #2 the client polls the list (`0x49` LOID; `s.cur` is not set), so the delay there depends on the client [HYPOTHESIS: setting `s.cur` on `0x49` would give type 4/5 pushes to File #2, unknown whether it handles them; not done].

### 6.15 Host migration: the game has it (2026-10-25)
- **[FACT, SLUS_207.65 disassembly]** When a partner is dropped (`0x1C7A14`: `+0x4C` = 0, `+0xF` decremented), the game recomputes the host: `0x1C71F0` = first active slot -> stored at `0x33505E` (`+0xE` of the table) and `0x1C7B10` queues event `0xF003 {1, dropped slot, new host}` in the local queue `0x332F90`. The dispatcher `0x1C8660` (called from `0x1C6510`) consumes it: removes the slot from the session's ordered list (`obj+0x28+0x48` count, `+0x4C...` u32 slots) and sets **"I am host" = (first slot of the list == my slot)** at `obj+0x28+0x44` (my slot at `+0x40`; getters `0x1C8800`/`0x1C8810`, wrapper `0x1C6660`). The session object is at `*(0x8147B8)`.
- **[FACT, BIN_8 = `netaq.bin`, base 0x810000]** Every frame (`0x8125D0`) netaq asks `0x1C6660` and, if I am host and latch `0x815D25` is 0, sets it to 1 and calls `0x812570` (takes authority: copies buffers `0x815830` -> `0x815630`/`0x815430`). `0x815D25` is read in 11 places in BIN_8. So: **migration is native and automatic; the game only needs to drop the host**. The only related string is "The room has been disbanded by the host." (BIN_3); nothing like "host has left".
- **Why it still stalls in production:** the runtime raised the partner timeout to 300 s (slow loads), so without notice the game takes up to 5 min to drop the host. ### 6.18 Tracker data between pages: `trk` / `REOGW-TRK` / `kk-peer-trk` (2026-11-03)
The game does not send each player's virus to the others (their copy stays at 5; see [tracker.md](tracker.md) "Online"). This is a channel of the page itself, outside the game relay. No new engine: the page takes the WebSocket the runtime opens (Emscripten calls `new WebSocket(url)`; the page wraps the constructor and keeps the one starting with `NET_URL`) and sends/receives text through it. The runtime ignores both texts.
- **Page -> gateway** (WebSocket text, `trkNetTick` every 1 s, only in an online game with a valid own slot, even if the tracker is closed; only if changed or every 3 s): `{"type":"trk","slot":n,"ch":c,"st":s,"virus":v,"av":a,"herb":h,"bleed":b}`. `slot` 0-3 = `+0x68` of the session; `ch` 0-7 character; `st` raw state byte (`+0xBA0`/`+0xBB8`); `virus` tenths of a percent (0-1000, virus/virusMax); `av`, `herb`, `bleed` raw game u16 (0-65535; the page shows them /60, /60 and /30).
- **Gateway -> server:** `"REOGW-TRK"` + u8 slot, u8 ch, u8 st, u16 virus, u16 av, u16 herb, u16 bleed (BE, 20 bytes) on each open UDP flow. It validates types and ranges (out of range or > 256 bytes: dropped) and sends **at most one per 400 ms per WebSocket**; the text also counts toward the session's frame quota like any text.
- **Server -> the others:** `"REOGW-TRK"` + u32 tag + the same 11 bytes (24 bytes), only to members of the same room still in their game (`playing` == room), never to the sender or another game/lobby. The sender must be in a game (`playing` == `cur`); at most one per 400 ms per session; validates length, slot <= 3, ch <= 7, virus <= 1000 (`trkRelay()`). No per-message log.
- **Gateway -> the others' page:** `{"type":"kk-peer-trk","tag":"xxxxxxxx","slot":n,"ch":c,"st":s,"virus":v,"av":a,"herb":h,"bleed":b}` (drops slot > 3, ch > 7, virus > 1000).
- **Receiving page:** keeps the latest per slot; uses it for that partner if it is <= 5 s old and has the same character as its game copy: virus, timers and the state except downed/dead/zombie (the game syncs those and they are newer). With no data (PCSX2, console, old page, stale data): "Virus -" and the rest from the game copy, as before. Cleared when the WebSocket closes.
- **Compatibility:** old gateway -> `guestControl` ignores types other than `left-scenario`; old server -> a datagram without the kk trailer is discarded; old gateway with new server -> every upstream `REOGW-*` is swallowed; old page with new gateway -> sends nothing, and ignores the `kk-peer-trk` text it receives (the runtime only looks at `kk-peer-gone`/`kk-peer-left`).
- **Cost:** <= 1 message/s per player in game (~100 bytes of text + 20 of UDP; x3 forwards of 24 bytes).
- **Tests [FACT]:** server `tests/TrkRelayTest.java` (in `tests/run-tests.sh`) and `tools/kktrk.py` against KkLocal (A-B in one game, C-D in another, E in the lobby: only B receives A's with its tag; 2 within 400 ms -> 1; invalid, stranger and lobby -> nothing; game data continues); the other battery tests still OK. Gateway: `go test` (`TestGuestTrk`, `TestUpstreamTrk`). See [tracker.md](tracker.md) "Partners' virus" for the native run and the page over RAM dumps.

## 8. 4 players (2026-10-20)
Native runs with 4 instances on a private stack with high gateway limits: one creates a 4-player room (RULE: down down right right on No. of Players), the other three enter staggered, the creator presses START and then each walks in turn.
- **Member list with 4 [FACT, read]:** a member record (`0x0A`) is 0x108 bytes (name, id, length, 0xF0 profile) and the kk header length field is 10 bits (`0x1DFDE4`: `& 0x3FF`). With 4 members the `0x0A` reply (0x42C payload bytes) does not fit: the server sent a truncated length and garbage bits in the flags. This is the most likely cause of the "4th player black before the room". The callback (File #1 BIN_3 `0x588120`, File #2 `0x5A08xx`) **accumulates** the records of each reply (counter `0x643D58`, zeroed on request, `0x58845C`) and only closes the request if the result has no request id (`+2`) or the message has flag `0x2000` (`+1 = 0`, dispatch `0x1DFE34`). Server: the list goes in parts of up to 3 records, intermediate ones with request id nonzero and without `0x2000`, the last with `0x2000`.
- **Reliable resends:** the client takes reliable messages strictly in order (`ctx+0x5C`); the server used to give up on an unacked message after 30 resends (30 s) and from then on everything after it was stuck for that client. Now it keeps resending (up to 600 s; the session drops earlier if the client is silent).
- **First-`0x0F` hold:** only reliable `0x0F` are held (up to 4096); unreliable ones for a member still loading are discarded (before, they filled the 512 queue and reliable ones were lost).
- **In-game timeout:** with the room in game, the session drops after 90 s without traffic (was 30 s; a long browser load could drop a player).
- **Room returning to waiting:** a `STAT` without `0x40000000` from the owner, or a `0x0A` from a member, sets it to "waiting" and clears bit `0x40000000` of the stored STAT (File #2 filters the list by STAT and the room stayed hidden forever).
- **Gateway:** the per-IP limit and handshake rate cut the 3rd/4th local Chrome (ERR204, DHCP). Now a rejected session is accepted and closed with code **4429** and the reason; the web runtime logs `[net] gateway refused the connection: <reason>` and retries every 20 s.
- **Cause of "one player does not enter START" [FACT, run]:** the owner sends the start in **a single datagram of several messages**: `0x10` class 3 to itself with flag **`0x0800`** (= multi-message packet) and the real seq, then `0x10` class 3 to each member and `0x08 STAT 0x40000000`. **Only the first header carries real seq/ack**; the following ones carry stale stack values (seen: seq 0 and 2692688956, both already used by that client). The server deduplicated each message by seq, so those for C and D were taken as resends and not forwarded: **C and D stayed in the waiting room** while A and B started. With 2 players this almost never collides; with 4, almost always. Fix: messages following a first message with `0x0800` are not deduplicated or acked separately (the packet is a resend if the first one is) and their ack field is ignored. Protocol test `server/tools/kk4.py` (5 simulated clients: 4-member list in 2 parts, START packet with stale seqs, resend, hold, latency, return to waiting and re-entry): all OK for File #1 and #2.

## 9. Real latency (2026-10-21)
- **Test bench (local, Linux):** one network namespace per client with veth pairs and `tc netem` on both ends (per direction: RTT/2 +- jitter/2 and loss), so the WebSocket (TCP) sees real retransmissions as on the internet (browser -> CDN -> gateway; the gateway -> server leg is local UDP and does not lose). A launcher starts the private stack and the native instances in their namespaces, and a summarizer digests the logs.
- **Simulated slow loading:** `PS2_DISC_DELAY_MS=<ms>` (native runtime, `disc.cpp`, tests only): every local disc read becomes ready that long after being requested, like the HTTP range waits on the web.
- **Production hypotheses (from logs):** (1) client silence during NOW LOADING -> `no traffic for 90 s` for both at once; (2) gateway sessions with "N frames in, 0 out": [FACT, read] the web runtime reopens the WebSocket 3 s after a cut (`websocket_web.cpp`), the gateway creates a new UDP flow (different source port) and the server ignored everything arriving with the session tag from another address (the anti-spoofing rule requires the ack of a pending reliable, which the client never received at the new address) -> the player stayed deaf until the 30 s timeout.
- **L1 [FACT]:** File #1, 2 players, 40 ms / 200 ms RTT, 1% loss per direction, jitter 10/40 ms, old server: both leave NOW LOADING (`game ready after 12.7 s` / `17.9 s, flushed 5`), 0x0F A->B 228 (108 with data), B->A 239 (120), both in J's Bar. **Latency and loss alone do not break online.**
- **Protocol test `server/tools/kkreconn.py` [FACT, ALL OK]:** B changes port mid-game -> `reconnecting from` -> receives the pending reliables -> `moved` -> data continues; `REOGW-BYE` of an old flow does not affect it; with BYE it returns within the grace and continues; a final BYE -> drops at 30 s.
- **L2 [FACT]:** as L1 + new server + new gateway + B with `PS2_DISC_DELAY_MS=150` from START: `game ready after 11.9 s` / `17.1 s, flushed 5`, A->B 399 (279 with data), B->A 243 (87); when the instances ended, the gateway sent BYE and the server said `connection closed (game 1001), waiting 30 s` and then dropped them. 150 ms per read barely lengthens the load (few large reads).
- **L3 [FACT, cause found]:** B with 3000 ms per read from START. A loads in 11.7 s and from then on sends **one reliable 0x0F per second** (`14 00 06 00 04 14 xx...`, byte xx grows by 0x20 each time: 0x49, 0x69...) waiting for the others; **it sends it 18 times and after ~27 s gives up**: sends `0x11` (result, 162 bytes), returns to the lobby (`0x0D`, `0x0C`, `0x0A`) and stays at **MEETING ROOM 1P**. B finishes loading at 34.0 s (`flushed 18`: it receives everything A sent, who is already gone) and enters an empty game; its later 0x0A sets the room "back to waiting". **The game itself waits ~20 s for everyone to finish loading**; if one takes longer (on the web: disc data over the internet), the fast one leaves by itself and the slow one is stuck in the load or cutscene. This explains "only 2 bytes", the asymmetric stuck cutscene and a production room that returned loading. It is not latency or loss.
- **The game's wait [FACT, read in the ELF]:** it is not a counter of 18 sends but a **per-partner timeout**. File #1: `0x1C76E0` walks the players (`0x335050 + 0x3C*i`, `+0x4C` active, `+0x54` last time heard) and if `clock (0x33506C) - last > 20.0` (float at **`0x235F50`**, read at `0x1C7A00`) it marks it dropped (`0x1C71F0`, `0x1C7B10`); the one loading sends nothing, so at 20 s the fast one considers it gone. There is another global timeout of 100.0 s without receiving anything (`0x235F68`, `0x1C6B38` -> `0x1C7AC0(4, ...)`). File #2: the same check at `0x1F32C0` with **31.0 at `0x241280`**. The `scripts/patches/` only patch overlays and this is ELF data, so the change lives in the runtime: `online_peer_timeout()` (`runtime/src/system.cpp`) raises it to **300 s** if it finds the original value. Downside: if a partner really drops mid-game, the others notice after 5 min (hence `REOGW-GONE`, 6.11).
- **Done in server/gateway:** session handoff on reconnect (`offer()`), `REOGW-BYE` close notice with 30 s grace, silence limits (waiting / in game), retention in order also of unreliable 0x0F with data (max 256), logs `silent for`, `game ready after`, `leaves ... s after START`, `reconnecting`/`moved`; the gateway sends a WebSocket ping every 15 s (cuts at 45 s).
- **Unverified / pending:** File #2 with slow loading in a real game; a real scenario end and return to the room with a slow client; why some rooms close 2-3 s after START (the new `leaves ... s after START` log will show it); gateway sessions with "N in, 0 out" (probably the ignored reconnection, now covered by `offer()`, unconfirmed in production). Note: forced TCP socket kill (`ss -K`) does not work on the WSL kernel, so reconnection was tested at protocol level, not with the game.
