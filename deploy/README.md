# outbreakweb.com deploy kit

Puts the site (landing page, `/file1/`, `/file2/`, `/admin`), the lobby server (Java, with the API and metrics) and the WebSocket gateway into production on a VPS (Ubuntu 24.04, host given by `$REO_HOST`), behind Cloudflare.

`REO_HOST` (the VPS address) is not stored in the repo: put it in `~/.config/reo/deploy.env`, e.g. `REO_HOST=vps.example.com`, and the scripts read it from there. Examples below use `$REO_HOST`.

**The kit does not upload discs or game ISOs, and will not ask for them.** Without a disc the game does not start, and that is expected. The translated game code (`ps2web.wasm` and `ps2web.data`) is **also not** uploaded unless `--with-game-code` is used, which is only for when the project owner explicitly approves it. Without that flag, the landing page, chat, rooms and `/admin` work, and the game pages load but do not start.

## What the operator does (once)

**Cloudflare** (verify):
1. DNS: `outbreakweb.com` and `www` -> `$REO_HOST`, proxied (orange cloud).
2. SSL/TLS -> **Full (strict)** mode. Origin Server -> an origin certificate for `outbreakweb.com` and `*.outbreakweb.com`, saved as `origin.pem` and `origin.key` in a private local folder outside the repo.
3. Network -> **WebSockets** ON. **IP Geolocation** ON (header `CF-IPCountry`, for the country shown in `/admin`).
4. Recommended: SSL/TLS -> Edge Certificates -> "Always Use HTTPS" ON. Security -> WAF -> a free rate-limiting rule on `/api/kk/register` and `/api/chat/send`.

**VPS provider:**
1. Panel firewall: 22, 80 and 443 open. The VPS itself also filters 80/443 so only Cloudflare gets in.
2. Your SSH public key loaded for root. **The private key never leaves your machine**: the scripts use the local `ssh` client.
3. Optional: snapshot the VPS before the first bootstrap.

## What the kit does

| File | Where it runs | What it does |
|---|---|---|
| `deploy.sh` | workstation (WSL) | `bootstrap` (once), deploy (each time), `--rollback`, `releases`, `package`, `fetch-backup`, `rotate` |
| `bootstrap.sh` | VPS (root, once) | `reo` user, key-only SSH, ufw, fail2ban, unattended-upgrades, 2 GB swap, UTC + NTP, journald (500 MB, 14 days), Caddy, Java 21, MariaDB, directories, secrets, units and timers |
| `remote/activate.sh` -> `reo-activate` | VPS | Installs a version into `/opt/reo/releases/<id>`, switches `current`, restarts, runs the health check and rolls back by itself on failure |
| `remote/health.sh` -> `reo-health` | VPS | Services, `/api/health`, `/`, `/file1/`, `/file2/` (200 + COOP/COEP), `/admin` requires basic auth, `/api/dev/*` closed, WebSocket `/eth` (101; 403 with another Origin), kk UDP 9090 on loopback, and nothing listening externally except sshd and Caddy |
| `remote/cf-ips.sh` -> `reo-cf-ips` | VPS (weekly timer) | Downloads Cloudflare's ranges, updates ufw (80/443) and Caddy's `trusted_proxies` |
| `backup.sh` -> `reo-backup` | VPS (daily timer, 07:30 UTC) | Dump of MariaDB + accounts + moderation + metrics + config, in `/opt/reo/backups`, 14 days |
| `remote/alert.sh` -> `reo-alert` | VPS (timer every 5 min) | Checks (reo-health + 5xx, exceptions, disk, RAM, backups, off-site download, TLS) and notifies the staff webhook when something fails, recovers, and every 6 h while it stays bad. The webhook is kept in the server's private config (never in the repo): `./deploy.sh rotate alerts` |
| `windows/fetch-backup-task.ps1` | workstation (Windows) | Daily scheduled task that runs `deploy.sh fetch-backup` (copies kept in a private local folder, keeps 30) |
| `status.sh` | workstation | Status, health, players, disk, RAM, bans, backups, latest errors; `logs` and `follow` |
| `admin.sh` | workstation | Moderation: `list`, `ban`, `unban`, `mute`, `unmute`, `purge` |
| `files/` | — | Production Caddyfile, `server.properties` and `gateway.json`, systemd units, sshd, fail2ban, journald |
| `tests/run-tests.sh` | workstation | shellcheck, `caddy validate`, gateway config, `systemd-analyze verify` |

On the VPS:
- `/opt/reo/releases/<date>-<commit>/` (web, admin, server, gateway, kit, VERSION) and `/opt/reo/current` -> the active one. `/opt/reo/{web,admin,server,gateway}` are links into `current/...`. The last 5 are kept.
- `/opt/reo/data/server/` (user `reo`, 0700): `kk-accounts.properties` (0600), `moderation.properties`, `blocked-names.txt` (optional, one word per line), `metrics/`.
- `/etc/reo/`: the server's private config: `server.properties`, `gateway.json`, `news.htm` (these ship with each release), plus files holding the database password, the admin token, the basic-auth credentials and the Cloudflare ranges (all root-only, 0600, generated by bootstrap).
- `/etc/caddy/`: `Caddyfile`, `tls/origin.{pem,key}`, the admin users file (bcrypt hash), `reo-cloudflare.caddy`.
- Services: `caddy` (80/443, the only public one besides sshd), `reo-server` (Java: app01 10127, regweb 8080, kk UDP 9090/9092, lobbies 8200/8300/8590/8690 and API 8088, all on 127.0.0.1), `reo-gateway` (127.0.0.1:8765), `mariadb` (127.0.0.1:3306). Metrics and the API are inside `reo-server` (no other process).

Production configuration highlights:
- Gateway: per-IP and global session limits, handshake and traffic rate limits per IP; `require_origin` and `origin_patterns` = `outbreakweb.com`; no pcap; the allowlist only points at the server's local ports.
- Server: `api.dev_login=false`, `packetlog.mode=off`, no sniffers, `us.kk.password` empty, `api.cors_origin=https://outbreakweb.com`, a limit on new names per IP per hour, metrics kept with 90 days of detail. The server applies rate limits and moderation.
- Real IP: Caddy takes `CF-Connecting-IP` only if the connection comes from a Cloudflare range and passes it on as `X-Real-IP`; the server and gateway trust that header only from loopback.
- Cache: file names have no hash, so everything is served with `Cache-Control: no-cache` (the browser revalidates with ETag and gets a 304). A TTL could pair an old `ps2web.js` with a new `ps2web.wasm` and break the game.
- Logs: journald, 14 days and 500 MB at most. Caddy keeps no access log (IPs).

## Order

Everything from WSL (`wsl -e bash -lc '...'` from PowerShell). Builds live in WSL and SSH goes out through the workstation's own OpenSSH client, with your key.

```bash
cd deploy
tests/run-tests.sh            # 0. local checks (optional)
./deploy.sh bootstrap         # 1. once: prepares the VPS and prints the secrets ONCE
./deploy.sh                   # 2. every time: build + package + upload + activation + health check
./status.sh                   # 3. check that everything is fine
```

1. `./deploy.sh bootstrap` copies the kit and the origin certificate (without displaying it) to a temporary directory on the VPS, runs `bootstrap.sh` and deletes the certificate copy. **At the end it prints the admin token and the basic-auth password exactly once**: store them in a password manager. They also remain on the VPS, root-only, in the server's private config. It can be repeated: it does not regenerate secrets or overwrite what already exists.
   - It does not cut the SSH session: it validates with `sshd -t` before reloading. If root has no `authorized_keys`, it does not disable passwords.
   - To limit port 22 to your IP: `REO_BOOTSTRAP_ENV="SSH_ALLOW_FROM=x.x.x.x" ./deploy.sh bootstrap`. Otherwise it stays open with `ufw limit` and fail2ban.
2. `./deploy.sh` builds both webs (`scripts/build_web.sh`), the jar (`setup.sh build`) and the gateway (`go test` + static build), assembles `deploy-out/reo-<id>.tar.gz`, uploads it over SSH (with a sha256 check) and runs `reo-activate install`. If the health check fails, it rolls back to the previous version by itself and the command exits with an error.
   - `--no-build`: packages what is already built.
   - `--with-game-code`: adds `ps2web.wasm`/`.data`. **Only with explicit approval of the project owner.**
   - Never included in the package: ISOs, discs, `games/`, `generated/`, `server/data/`, pcaps, logs, memory cards, certificates. The script verifies this before packaging and the VPS verifies it again when unpacking.
3. `./deploy.sh --rollback` goes back to the previous version (with its configuration). `./deploy.sh releases` lists versions (`*` = active).

## /admin

`https://outbreakweb.com/admin` first asks for the browser's **basic auth** (the credentials printed by bootstrap) and then the **admin token** (`REO_ADMIN_TOKEN`), which the page keeps only while the tab is open. `/api/admin/*` requires the same.

If you lost them, rotate them (see "Rotating secrets") or read them as root from the server's private config.

## Moderation

```bash
./admin.sh list
./admin.sh ban name PlayerA 0 spam        # 0 = permanent; also deletes their messages
./admin.sh mute name PlayerA 60 flood     # 60 minutes without writing (reason: a single word)
./admin.sh ban ip 203.0.113.9 1440
./admin.sh unban name PlayerA
./admin.sh purge name PlayerA             # deletes their messages without banning
```
**Directly from PowerShell** (without WSL; uses the Windows `ssh` and the same key):
```powershell
ssh root@$REO_HOST "reo-admin list"
ssh root@$REO_HOST "reo-admin mute name PlayerA 60 insults"   # <action> name|ip <who> <minutes> <reason>
ssh root@$REO_HOST "reo-admin unmute name PlayerA"
ssh root@$REO_HOST "reo-status"
ssh -t root@$REO_HOST "journalctl -f -u reo-server"           # live logs
```
When called from PowerShell via `wsl -e bash -lc "cd deploy && ./admin.sh ..."`, the `ssh.exe` launched from WSL used to fail with `ssh.exe: Invalid argument` (stdin was the Windows console passed through WSL and the working directory a `\\wsl.localhost` path). `lib.sh` now launches `ssh.exe` from `/mnt/c` and with stdin on `/dev/null` when nothing is piped in; `status.sh follow` (needs a terminal) may still fail there: use the `ssh -t` line above. From Git Bash everything works as before. There is also the `/admin` -> Moderation panel (live chat, players, sanctions and log).

The token never leaves the VPS: `admin.sh` calls `reo-admin` over SSH, which reads it from the server's private config. For extra banned names: one word per line in `/opt/reo/data/server/blocked-names.txt`, then `systemctl restart reo-server`.

## Rotating secrets

```bash
./deploy.sh rotate admin-token    # new REO_ADMIN_TOKEN, restarts reo-server
./deploy.sh rotate basic-auth     # new /admin password, reloads Caddy
./deploy.sh rotate db             # new MariaDB password, restarts reo-server
```
Each prints the new value once.
- **Origin certificate:** generate a new one in Cloudflare, save it in your private local folder and run `./deploy.sh bootstrap` again (reinstalls the certificate and leaves everything else as is).
- **SSH key:** add the new one to root's `authorized_keys` (and the `reo` user's), test logging in with it, and only then remove the old one.

## Logs and status

```bash
./status.sh                      # summary
./status.sh logs reo-server 200  # reo-server | reo-gateway | caddy | mariadb | fail2ban (empty = our three)
./status.sh follow reo-gateway   # live
```
On the VPS: `journalctl -u reo-server -f`, `reo-health`, `reo-activate list`, `systemctl list-timers 'reo-*'`.

## Backups

- `reo-backup.timer` runs daily at 07:30 UTC and leaves `/opt/reo/backups/reo-<date>.tar.gz` (0600). They are deleted after 14 days. To make one now: `ssh root@$REO_HOST reo-backup`.
- Pull the latest to the workstation: `./deploy.sh fetch-backup` -> a private local backups folder (or another folder: `./deploy.sh fetch-backup /mnt/c/other/folder`). **It contains credentials** (accounts, token and certificate): treat it with the same care as your other secrets. If the file is already there it is not downloaded again; the 30 newest are kept (`REO_BACKUP_KEEP`) and the download is marked on the VPS.
- Automatic download: in PowerShell, run `windows/fetch-backup-task.ps1` (with `powershell -ExecutionPolicy Bypass -File`) to create the scheduled task "reo-fetch-backup" (daily at 12:00 and at login; if the PC was off it runs when turned on). `-Remove` deletes it, `-RunNow` tests it. If 3 days pass without a download, `reo-alert` notifies the staff channel.
- Restore (on the VPS): `systemctl stop reo-server`; `tar -xzf reo-....tar.gz -C /tmp/r`; `mariadb < /tmp/r/mariadb.sql`; `cp -a /tmp/r/opt/reo/data/server/. /opt/reo/data/server/`; `chown -R reo:reo /opt/reo/data/server`; `systemctl start reo-server`.

## If something fails

| Symptom | What to do |
|---|---|
| `deploy.sh` says "UNHEALTHY: rolling back" | It already went back to the previous version. Check `./status.sh logs` and fix before deploying again. |
| Cloudflare error 521/522 | Caddy down or the firewall not letting Cloudflare in: `./status.sh`; on the VPS, `systemctl status caddy`, `ufw status \| grep reo-cf \| head` and `reo-cf-ips`. |
| Error 525/526 | Origin certificate expired or badly installed: `openssl x509 -in /etc/caddy/tls/origin.pem -noout -enddate`. |
| The game says "No online connection" | `./status.sh` (the `wss /eth` line). If the gateway is full, the browser receives close code 4429; see `limits` in `files/gateway.json`. |
| `/api/*` returns 502 | `reo-server` down or starting: `./status.sh logs reo-server`. It needs MariaDB (`systemctl status mariadb`). |
| Locked out of SSH | Use the provider's web console (VNC) as root: `rm /etc/ssh/sshd_config.d/00-reo.conf; systemctl reload ssh`, or `ufw disable`. |
| Disk full | `./status.sh` (resources); `journalctl --vacuum-size=200M`; delete old versions in `/opt/reo/releases`. |
| Manual rollback | `./deploy.sh --rollback` or, on the VPS, `reo-activate rollback`. |

## Kit tests

`tests/run-tests.sh` (local, no VPS): shellcheck of all scripts, `caddy validate` and `caddy fmt` of the Caddyfile (with a throwaway self-signed certificate), the gateway loading `files/gateway.json`, the production switches of `server.properties`, and `systemd-analyze verify` of the units. A full rehearsal in an Ubuntu 24.04 container (systemd-nspawn) is possible but is not documented in the public repo.
